# 智能温室大棚监测系统 · PC 上位机 —— 项目总结文档

> **本文档的用途**：把「PC 上位机」这个软件的角色、定位、界面结构与功能完整讲清楚，
> 供 **Gemini** 阅读后为该软件生成若干套**适配的应用程序图标（App Icon）**。
> 文末第 11 节是给 Gemini 的图标设计输入区，前面的 1–10 节是它理解「这个软件到底是什么、气质应该怎样」所需的事实依据。

---

## 1. 一句话定位

**这是一款运行在 Windows 上的「智能温室大棚」桌面监测上位机**：它用串口把温室里的 STM32 下位机接进电脑，把一条条串口文本变成实时数字卡片、四条趋势曲线、双状态图标和日志流；再通过 MQTT 把数据推上云端，同时把手机端发来的控制指令原样透传回单片机。

它是整个「**手机 App → MQTT Broker → 串口 → 单片机**」远程控制链路里，坐在正中间的那个**中枢网关 + 可视化控制台**。

- **STM32 固件（下位机）**：1.5 秒一帧采集 DHT11 温湿度、D2-5-2K 电容式土壤湿度、光敏光照、MQ-2 烟雾；OLED 实时显示；LED + 蜂鸣器声光报警；自动模式下报警联动舵机（天窗）与电机（风扇）。
- **PC 上位机（本项目，主角）**：**串口网关 + 数据可视化 + 云端桥接**。
- **EMQX 服务器**：MQTT Broker，PC 端走 1883/TCP，小程序走 8083/WebSocket；配套一个 C# 写的「一键启动器」（自动定位 EMQX、后台启动、轮询 18083 控制台就绪后自动打开浏览器）。
- **微信小程序**：温室主题轮播首页 + 五项环境数据展示 + 执行器远程控制 + 报警横幅与震动提醒。

## 5. 功能清单（分五大能力）

### 5.1 能力一：串口接入与环境数据解析

- 自动枚举本机可用串口（`SerialPort.GetPortNames()`），一键刷新；默认波特率 **9600, 8N1**。
- 后台线程 `DataReceived` 收字节 → 累积到 `StringBuilder` 缓冲区 → 按 `\r\n` / `\r` / `\n` 三种换行切行 → 逐行解析（正确处理「一帧被拆成两个串口事件」的半包问题）。
- **正则逐字段解析**，与固件输出协议一字不差：

  | 字段 | 正则 | 含义 |
  | --- | --- | --- |
  | 温度 | `Temp:(-?\d+(?:\.\d+)?)C` | 支持零下负温 |
  | 空气湿度 | `Humi:(\d+(?:\.\d+)?)%RH` | 相对湿度 |
  | 土壤湿度 | `Soil:(\d+)%` | 百分比（固件已做反比映射） |
  | 光照强度 | `Light:(\d+)%` | 百分比 |
  | 天窗 | `Servo:(ON\|OFF)` | 舵机状态 |
  | 风扇 | `Motor:(ON\|OFF)` | 电机状态 |
  | 空气质量 | `Air:(nice\|bad)` | MQ-2 烟雾判定 |

- **鲁棒解析策略（重要的设计特征）**：
  - **单字段异常不丢弃整帧** —— 全部改用 `TryParse`，某个字段坏了，其余字段照常刷新。
  - **DHT11 读取失败可容错** —— 固件读不到温湿度时只输出其余字段，上位机识别为 `HasTempHum = false`，跳过温湿度卡片与曲线更新，但土壤/光照/执行器状态依然实时刷新，不会整屏卡死。
  - **先校验后写状态** —— 数值合理性检查（温度 −50～100 °C、湿度 0～100%）放在写入全局状态之前，非法帧不会污染已有数据。
  - **全链路 `InvariantCulture`** —— 小数点永远是 `.`，避免德语区/法语区电脑把 JSON 拼成 `25,5` 导致小程序 `JSON.parse` 直接失败。

### 5.2 能力二：实时可视化仪表盘

- **8 张圆角数据卡片**：温度、湿度、土壤湿度、光照强度、空气质量、窗户、风扇、蜂鸣器。
  - 每张卡片 = **图形图标 + 名称 + 单位 + 大号读数**，左侧一道 3px 主题色竖条（`CardPanel` 自绘：白底 + 10px 圆角 + 1px 描边 + 双缓冲防闪烁）。
  - 数值型读数 17pt 粗体（Arial），状态型读数 13pt（「nice」「关闭」「静音」）。
  - **双状态图标随报警实时切换**：温度/湿度/土壤/空气/窗户/风扇/蜂鸣器都有「正常 ↔ 报警 / 关 ↔ 开」两套 PNG，每帧根据阈值自动换图换色。
- **GDI+ 手绘趋势图**（不依赖任何第三方图表控件）：
  - **双 Y 轴**：左轴温度 `0–40 °C`（红），右轴湿度 `0–100 %`（蓝）；10 × 10 点状网格；两轴刻度与网格线精确重合。
  - **四条曲线**：温度（红 `#F44336`）、湿度（蓝 `#2196F3`）、土壤湿度（黄 `#FFC107`）、光照（橙 `#FF9800`）；每条线都带半透明宽描边阴影 + 实心数据圆点。
  - 保留最近 **100 组**数据点，标题实时显示 `数据点数: 87/100`；右上角图例色块+文字。
- **指示灯式状态**：串口状态、MQTT 状态、当前模式都用「● 文字 + 颜色」表达（灰=未连接 / 绿=已连接或自动 / 橙=手动或过渡）。
- **运行日志窗**：等宽 `Consolas` 字体、毫秒级时间戳、按事件类型着色（绿=解析成功、红=错误、蓝=发送、紫=MQTT 接收、橙=警告）；支持「自动滚动」开关；日志超 6 万字符自动裁掉前半段，防止长时间运行卡顿。

### 5.3 能力三：MQTT 上行 —— 数据上云

- 可配置 Broker 地址，容忍 `host` / `host:port` / `mqtt://host:port` 三种写法，非法端口给出明确提示（而不是抛异常崩溃）。
- 客户机 ID 唯一（`DHT11_Client_ + GUID`），`CleanSession`。
- **每帧数据自动发布为 JSON**（主题默认 `green/data`，QoS 1，不保留）：

  ```json
  {
      "timestamp": "2026-10-25 15:30:45.123",
      "temperature": 26.5,
      "humidity": 60.0,
      "soilMoisture": 35,
      "lightPercent": 72,
      "airQuality": "nice",
      "servoStatus": "OFF",
      "motorStatus": "OFF",
      "alarmType": "温度报警",
      "hasAlarm": true
  }
  ```

- 「**自动发布数据到 MQTT**」复选框可随时开关上行推送。
- 每次发送都在日志里留一行 `[MQTT发送] 温度:… 湿度:… 土壤湿度:… 光照:… 空气:… 报警:…` 便于现场排障。

### 5.4 能力四：MQTT 下行 —— 远程指令透传

- 订阅控制主题（默认 `green/control`），收到任意 payload 后**原文 `WriteLine` 到串口**，固件端 `Parse_Command_Frame()` 直接执行。
- 因此**小程序、MQTTX、任意 MQTT 客户端都能控制这台温室**，上位机不需要认识指令语义 —— 它是一条纯粹的透传管道。
- 若串口未打开，日志会明确提示「串口未连接，无法转发消息」而不是静默丢弃。
- 支持的指令集：

  | 指令 | 作用 |
  | --- | --- |
  | `mode-0` / `mode-1` | 切换自动 / 手动模式 |
  | `DUOJ-0` / `DUOJ-1` | 天窗舵机关（0°）/ 开（180°） |
  | `MOTOR-0` / `MOTOR-1` | 风扇停 / 全速 |

### 5.5 能力五：本地控制、告警判定与数据留存

- **设备控制条**：自动/手动模式切换；切到自动模式时，窗户/风扇四个手动按钮自动置灰禁用（带右侧灰字提示），避免与固件自主联动打架。
- **统一报警阈值（三端一致，固件为权威判定源）**：

  | 指标 | 报警条件 | 联动 |
  | --- | --- | --- |
  | 温度 | > **26 °C** | 黄灯 + 天窗开 180° + 蜂鸣器 |
  | 空气湿度 | > **85 %RH** | 黄灯 + 天窗开 180° + 蜂鸣器 |
  | 土壤湿度 | > **40 %**（过湿） | 蓝灯 + 蜂鸣器 |
  | 空气质量 | 烟雾判定 `bad` | 红灯 + 浓烟灯 + 风扇全速排风 + 蜂鸣器 |
  | 光照强度 | —— | **仅采集展示，不参与报警** |

- **报警类型判定**（写入日志、CSV 和上行 JSON 的 `alarmType`）：
  `温度湿度报警` / `温度报警` / `湿度报警` / `土壤过湿报警` / `空气污染报警` / `正常`。
- **CSV 数据导出**：一键导出全部历史记录，列头为
  `序号, 温度(°C), 湿度(%), 土壤湿度(%), 光照(%), 空气质量, 窗户状态, 风扇状态, 报警类型, 时间戳`，
  统一 `InvariantCulture` 格式化，Excel 直接可开。
- **登录鉴权与注销回流**：`admin / admin` 本地鉴权（单机演示定位，接口预留可换真实鉴权），注销后回到登录页可重新进入。

## 6. 技术亮点（这个软件「不业余」的地方）

1. **跨线程 UI 安全统一收口** —— 所有后台线程（串口回调、MQTT 回调）的界面更新都走 `SafeInvoke()`，内部吞掉 `ObjectDisposedException` / `InvalidOperationException`。修掉了「关窗瞬间后台线程二次抛异常逃逸到线程池、.NET Framework 直接终止进程」这个真实崩溃。
2. **图标缓存防 GDI+ 句柄泄漏** —— 固件 1.5 s 一帧、每帧最多换 10 个图标，约 2.4 万张/小时，原写法会耗尽 GDI+ 句柄且长期锁定 PNG 文件。改为进程内 `Dictionary` 缓存 + 先读内存再解码（解码后立刻关闭文件句柄），并记住「文件不存在」避免每帧重复查盘。
3. **响应式布局单一真源** —— 所有坐标只在 `ApplyResponsiveLayout()` 一处计算，`Resize` 只负责触发重算。
4. **日志自回收** —— 用 `_logCharCount` 记账而非每帧读 `TextLength`，超 6 万字砍掉前半段。
5. **MQTT 处理器只挂一次** —— 用 `_mqttHandlerAttached` 防重，避免「断开→重连」一次就多挂一份处理器，导致小程序按一次开窗、单片机收到 N 条 `DUOJ-1`。
6. **关窗不僵死不卡死** —— MQTT 断开动作丢到线程池执行，UI 线程只做带超时的等待（`Task.Wait(1500)`），超时照样继续关窗，最终无论成败都 `Dispose` 客户端。
7. **DPI 自适应钳制** —— 初始尺寸取 `Math.Min(1380, 工作区宽度 − 24)`，避免高分屏 150% 缩放时窗口跑到屏幕外。
8. **版本号写进标题** —— `智能温室监测系统 v2.5.0`，一眼能看出跑的是哪个版本，排查「双击后好像没更新」这类问题。

## 7. 数据流与状态机（一帧数据的完整旅程）

```
① STM32 每 1.5s 打印一行：
   Temp:26C   Humi:60%RH   Soil:35%(raw=1200)  Light:72%  Servo:OFF Motor:OFF  Air:nice

② 串口 9600/8N1 逐字节到达 PC → StringBuilder 缓冲 → 按换行切行

③ ParseData() 正则拆字段 → FrameData{ HasTempHum, Temp, Hum }
   ParseSTM32ExtendedData() 拆扩展字段 → 写 _waterLevel/_lightLevel/_servoStatus/_motorStatus/_airQuality

④ SafeInvoke 切回 UI 线程：
   ├─ 刷新 8 张卡片读数与双状态图标
   ├─ GetAlarmType() 判定报警类型 → UpdateAlarmStatus() 换报警图标 + 写日志
   ├─ AddToChart() 追加一组数据到 4 条曲线（超 100 点丢弃最早）
   └─ PublishDataToMqtt() 组装 JSON → green/data (QoS1)

⑤ 反向：小程序发布 green/control
   → OnMqttMessageReceived → SafeInvoke →_serialPort.WriteLine(payload)
   → STM32 Parse_Command_Frame() 执行 → 下一帧数据回显真实状态
```

**闭环特征**：控制指令下发后，设备真实状态会通过下一帧 `Servo:` / `Motor:` 字段回显到界面和小程序 —— 是**有反馈闭环的控制**，不是单向的「发出去就不管了」。

## 9. 视觉气质与设计语言（已实现的界面风格）

在为这个软件设计图标前，需要理解它**既有的、已经落地的**视觉语言 —— 新图标应当延续而不是背离它。

- **整体调性**：浅色、干净、克制。白卡片浮在冷灰底（`#F4F6F9`）上，没有重阴影、没有玻璃拟态、没有霓虹发光。
- **色彩语义固定且一致**：
  - **绿 `#4CAF50`** = 正常 / 连接成功 / 自动模式 / 植物生长 ← 温室系统的主情绪色
  - **蓝 `#2196F3`** = 湿度 / 数据 / 技术属性
  - **红 `#F44336`** = 温度 / 报警 / 危险
  - **橙 `#FF9800`** = 警告 / 手动模式 / 光照
  - **深蓝灰 `#34495E`** = 标题与主要文字
- **形状语言**：圆角矩形（半径 10–12px）、细描边（1px `#E4E8EE`）、左侧 3px 主题色竖条作为「数据卡片」的身份标记。
- **功能图标风格（逐像素实测）**：`ICON/` 下 16 个在用 PNG 全为 **128×128、透明背景、单色描边线稿**，无渐变、无投影、无圆角底。它们自成一套**状态色语义**，比界面 UI 色更「传统图标味」：

  | 状态 | 色值 | 出现位置 |
  | --- | --- | --- |
  | 常态 / 正常 / 开启 | **`#1296DB`**（蓝） | 温度、水位、光照、空气质量优、窗户-开 |
  | 湿度专属 | **`#00A0E9`**（亮蓝） | 湿度 |
  | 报警 / 异常 | **`#D81E06`**（中国红） | 温度_报警、湿度_报警、水位_报警、空气质量劣、蜂鸣器-开 |
  | 风扇开启（唯一双色） | **`#1C86E5`** + `#80E1FF` 高光 | 风扇-开 |
  | 关闭 / 静默 | **`#515151`**（窗）/ **`#8A8A8A`**（风扇）/ **`#2C2C2C`**（蜂鸣器） | 三类「关」状态 |
- **字体**：中文「微软雅黑」，数字用「Arial / Consolas」等宽感字体，强调「读数」而非「装饰」。
- **旧应用图标（逐像素取色的完整构成）** —— 这是本次要替换的对象，理解它才能知道「要延续什么、要改掉什么」：

  | 层级 | 内容 | 实测色值 |
  | --- | --- | --- |
  | 底色 | 深墨绿满幅背景 | `#023A31` / `#033830` |
  | 主体磁贴 | 圆角方形（squircle），占画幅约 70%，上→下绿渐变 | `#02BD6E` → `#01B669` → `#006F68` |
  | 顶部符号 | 三段青色 WiFi 弧 | `#2FFCEB` / `#30F0F1` |
  | 中部主体 | 半透明玻璃穹顶温室 + 白色骨架线 + 畦内幼苗 | 壳体 `#028E6B`，叶片 `#55B27B`，土壤 `#136769` |
  | 环绕装饰 | 青色电路走线 + 圆形焊点 | `#009D6D` ~ 亮青 |

  **它的优点**：配色统一、有「温室 + 物联网 + 数据」三重含义、缩到 128 px 仍然清晰。
  **它的可改进处**：元素多达 5 层（背景色 + 磁贴 + WiFi 弧 + 温室 + 电路走线），到 **48 px 以下电路走线与焊点会糊成一团**，WiFi 蹄形波也是最常见的物联网陈词滥调。新方案应当在**保留「青绿 + 温室 + 苗」基因**的前提下**减少层级、去掉细走线**。

## 10. 与「图标」直接相关的设计约束

一个真正的 Windows 应用程序图标要能经受住这些考验，请 Gemini 在生成时一并考虑：

1. **尺寸阶梯**：需同时可在 **16 / 32 / 48 / 64 / 128 / 256 px** 下辨认。16 px 时要靠「一个大形状 + 一个强对比色」立住，不能靠细节。
2. **形态**：Windows 桌面应用习惯 **圆角方块（Squircle / superellipse）** 承载图形；图标需在 256 px 画布内留出约 8–10% 安全边距。
3. **色彩对比**：主色建议落在绿色系。**两套既有色板都可作为锚点**（选一套为主、另一套为辅，不要混着用）：
   - **界面 UI 色（Material 系）**：绿 `#4CAF50`、蓝 `#2196F3`、红 `#F44336`、橙 `#FF9800`、深蓝灰 `#34495E`、页底 `#F4F6F9`。
   - **功能图标色（实测）**：常态蓝 `#1296DB`、报警红 `#D81E06`。
   - **旧应用图标色（实测）**：深墨绿底 `#023A31`、绿渐变 `#02BD6E → #006F68`、信号青 `#2FFCEB`。
   深色版与浅色版的识别度都要成立。
4. **禁止项**：不要写实照片、不要长段文字（最多 1–2 个字母或无文字）、不要超过 3 层视觉层级、不要细小到 16 px 会消失的线条（如 1 px 电路走线、密集网格）。
5. **避免陈词滥调**：WiFi 蹄形波 + 齿轮 + 云 + 灯泡堆叠是「AI 生成物联网图标」的典型套路；希望能有更具体、更有温室/植物/数据仪表意味的隐喻。
6. **必须能被工程直接采用**：最终产物要能转成 **`.ico`（含 256/128/64/48/32/16 六个尺寸的 32bpp 图像）** 塞进 `DHT11.csproj` 的 `<ApplicationIcon>`，因此请**避免大面积纯透明背景**（Windows 任务栏浅色主题下会糊），也避免极细描边。

## 13. 附：实现与文档的已知不一致（不影响图标设计，但联调须知）
